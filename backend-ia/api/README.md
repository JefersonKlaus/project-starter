# AWS Lambdas (`backend-ia/api`)

Five Lambda functions (see `infra/`). The API Gateway of the stack is a
WebSocket API authenticated with Amazon Cognito (see "WebSocket API");
`lambda_create` and `lambda_status` are also reachable directly through their
public Lambda Function URLs, which have no authentication.

| Lambda               | Exposed as               | Purpose                                                                  |
| -------------------- | ------------------------ | ------------------------------------------------------------------------ |
| `lambda_create/`     | Function URL (`POST`)    | Generates an AWS serverless architecture from a product description      |
| `lambda_status/`     | Function URL (`GET`)     | Health check: verifies the dependencies `lambda_create` needs            |
| `lambda_ws_connect/` | WebSocket `$connect`     | Verifies the Cognito token of the client opening the connection          |
| `lambda_ws_prompt/`  | WebSocket `prompt`       | Validates the message and starts the generation asynchronously           |
| `lambda_ws_worker/`  | (invoked by `ws_prompt`) | Runs the generation (`lambda_create`) and pushes the result to the client |

Each folder is deployed as a plain **zip package** with a dependencies layer:
no container image, no embeddings model inside the Lambda. The zip is flat
(`main.py` at its root, entry point `main.lambda_handler`), which is why the
modules import each other as top-level modules (`import orchestrator`,
`from ai.rag import ...`).

## Lambdas

One sub-section per Lambda. They share the same layout (handler -> orchestrator
-> serializer / service / output, one responsibility per module) and the same
packaging, so only what is specific to each one is described.

### Architecture generation (`lambda_create`)

`lambda_create/main.py` is exposed through its Function URL (`POST`,
output `lambda_create_url`) and is what the WebSocket worker runs. It receives a product
description and returns a complete serverless design for it: the AWS services,
a Mermaid diagram and the Terraform and Python code, generated by a Groq-hosted
LLM guided by reference implementations (RAG). What it does, in order:

| Step         | What it does                                                                                           |
| ------------ | ------------------------------------------------------------------------------------------------------ |
| `parse`      | Decodes the proxy event body (JSON, base64 aware) into `RequestPayload` (`prompt` is required)         |
| `rag_index`  | First invocation of a container: downloads `s3://$RAG_S3_BUCKET/$RAG_S3_KEY` and builds the BM25 index |
| `rag_search` | Enriches the prompt with AWS/serverless terms and picks the 3 best reference chunks                    |
| `generate`   | Sends system rules + RAG context + prompt to Groq (`openai/gpt-oss-120b`, JSON mode, up to 3 attempts) |
| `validate`   | Parses the answer into `AWSArchitecture` (Pydantic); invalid JSON triggers a retry, schema errors fail |
| `respond`    | Proxy response with the architecture, `rag_references` for auditing and CORS headers                   |

Request flow and responsibilities:

```
main.py -> orchestrator.py -> request_parser.py (input: models.RequestPayload)
                           -> service_architecture.py -> service_ai.py -> ai/rag.py / ai/machine.py
                           -> response.py (output)
```

| Module                    | Responsibility                                                         |
| ------------------------- | ---------------------------------------------------------------------- |
| `main.py`                 | Lambda handler; delegates to the orchestrator                          |
| `orchestrator.py`         | Runs parse -> service -> response and maps failures to HTTP statuses   |
| `request_parser.py`       | Serializer: API Gateway event -> `models.RequestPayload` (400/422)     |
| `models.py`               | Input model (`RequestPayload`)                                         |
| `service_architecture.py` | Service: RAG lookup + generation + audit references                    |
| `service_ai.py`           | Service: downloads the RAG index from S3, caches the index and the LLM |
| `response.py`             | Output: proxy response with JSON body and CORS headers                 |
| `config.py`               | Environment variables (and `.env` for local runs)                      |
| `ai/rag.py`               | BM25 search over `rag_index.json`                                      |
| `ai/machine.py`           | Prompt and Groq model invocation                                       |
| `ai/models.py`            | Output schema (`AWSArchitecture`) validated with Pydantic              |
| `run_local.py`            | Local tool: invokes the handler on your machine (see "Run locally")    |
| `../../rag/ingest.py`     | Local tool: builds `rag_index.json` from the reference Python files    |

On success (`200`) the body is the `AWSArchitecture` schema plus `rag_references`:

| Field                      | Content                                                                          |
| -------------------------- | -------------------------------------------------------------------------------- |
| `analysis_date`            | `YYYY-MM-DD` (always today's date, even if the model gets it wrong)              |
| `mermaid_diagram`          | Mermaid code of the flow, using the same Lambda/file names as the generated code |
| `aws_services`             | `[{"service": "AWS Lambda", "resource_name": "create_task"}, ...]`               |
| `generated_code.terraform` | `{"main.tf": ..., "variables.tf": ..., "outputs.tf": ...}` (complete HCL)        |
| `generated_code.python`    | `{"create_task.py": ..., "requirements.txt": ...}` (one file per Lambda/action)  |
| `rag_references`           | Source paths of the reference chunks that were sent to the model (audit)         |

```json
{
  "analysis_date": "2026-10-26",
  "mermaid_diagram": "graph LR\n    subgraph API_Gateway[API Gateway] ...",
  "aws_services": [
    { "service": "AWS Lambda", "resource_name": "create_task" },
    { "service": "Amazon API Gateway", "resource_name": "todo_api" },
    { "service": "Amazon DynamoDB", "resource_name": "tasks_table" }
  ],
  "generated_code": {
    "terraform": { "main.tf": "...", "variables.tf": "...", "outputs.tf": "..." },
    "python": { "create_task.py": "...", "requirements.txt": "..." }
  },
  "rag_references": ["/path/to/reference/handler.py", "..."]
}
```

Generation gets `MAX_TOKENS` (32k) of output per request; gpt-oss is a
reasoning model, so its "thinking" tokens count against that budget. If the
answer is still cut off, Groq rejects it (`json_validate_failed` with an
unfinished `failed_generation`) and the function fails fast with `500` /
`"The model output was cut off at ... tokens"` instead of retrying: only a
malformed-but-complete JSON is retried (up to 3 attempts). Files whose line
breaks came back double-escaped (`\\n`) are normalised after validation.

The RAG index, the BM25 index and the Groq client are cached at module level,
so warm containers skip the S3 download and client setup. A full run takes
tens of seconds (the Terraform timeout is 300 s); the generation rules the model
must follow (one Lambda per action, least-privilege IAM, proxy responses, ...)
live in `SYSTEM_RULES` in `ai/machine.py`. See "Request and response" for the
request body, the `curl` example and the error codes.

### Health check (`lambda_status`)

`lambda_status/main.py` answers `GET` on its Function URL (output
`lambda_status_url`). Besides proving the service answers, it verifies the
dependencies `lambda_create` needs at runtime, without downloading or
generating anything:

| Check          | What it does                                                                 |
| -------------- | ---------------------------------------------------------------------------- |
| `rag_index`    | `HeadObject` on `s3://$RAG_S3_BUCKET/$RAG_S3_KEY` (the RAG index exists)     |
| `groq_api_key` | `GROQ_API_KEY` is set (the value is never returned)                          |
| `groq_hello`   | Sends a minimal "hello" chat completion to Groq (key accepted, model usable) |

```bash
curl -i "$(terraform -chdir=infra output -raw lambda_status_url)"
```

It returns `200` when every check passes and `503` otherwise (so it can drive
an uptime monitor), always with the result of each check:

```json
{
  "status": "error",
  "message": "One or more dependencies are unavailable",
  "checks": {
    "rag_index": { "status": "error", "detail": "s3://sandbox-...-rag/rag_index.json not found" },
    "groq_api_key": { "status": "ok", "detail": "GROQ_API_KEY is set" },
    "groq_hello": { "status": "ok", "detail": "Groq answered a hello request with model openai/gpt-oss-120b" }
  }
}
```

Behaviour worth knowing:

- The Groq call uses the same model as `lambda_create` (`GROQ_MODEL` overrides
  it), capped at 10 s with no retries, so a Groq outage shows up as a quick
  `503` instead of a Lambda timeout.
- A check that crashes is reported as `error`; it never hides the other results.
- Environment: `GROQ_API_KEY`, `RAG_S3_BUCKET`, `RAG_S3_KEY` and the optional
  `GROQ_MODEL`. IAM (Terraform): `s3:GetObject` on the index and `s3:ListBucket`
  on the bucket, so a missing index is reported as `404` rather than `403`.
- Dependencies: the `groq` SDK and `python-dotenv` (`lambda_status/requirements.txt`,
  shipped as a layer) plus `boto3` from the runtime.

```
main.py -> orchestrator.py -> service_health.py -> checks/rag_index.py | groq_api_key.py | groq_hello.py
                           -> response.py (output)            (results: models.CheckResult / HealthReport)
```

| Module                   | Responsibility                                                                      |
| ------------------------ | ----------------------------------------------------------------------------------- |
| `main.py`                | Lambda handler; delegates to the orchestrator                                       |
| `orchestrator.py`        | Runs the service and maps the report to `200` (healthy) or `503`                    |
| `service_health.py`      | Registry of checks wired to `config`; runs them all, a crash never hides the others |
| `checks/rag_index.py`    | `HeadObject` on the RAG index (S3)                                                  |
| `checks/groq_api_key.py` | `GROQ_API_KEY` is set                                                               |
| `checks/groq_hello.py`   | Minimal chat completion against Groq                                                |
| `models.py`              | `CheckResult` (one check) and `HealthReport` (all checks, `healthy`, `to_dict`)     |
| `response.py`            | Output: proxy response with JSON body (`success` / `unavailable`)                   |
| `config.py`              | Environment variables (and `.env` for local runs)                                   |
| `run_local.py`           | Local tool: invokes the handler on your machine (see "Run locally")                 |

Adding a dependency check is one new module in `checks/` (a plain function of
its inputs, e.g. `rag_index.check(bucket, key)`) and one entry in
`service_health.CHECKS`.

### WebSocket API

A plain HTTP `POST` to `lambda_create` keeps the connection open for the whole
generation (tens of seconds). The WebSocket API, the only API Gateway of the
stack, does the same job asynchronously: you connect, send the prompt, get an
immediate acknowledgement and receive the result as a message when it is ready.

```
client --$connect--> lambda_ws_connect  (Cognito JWT verification: 200 accepts, 401 rejects)
client --prompt----> lambda_ws_prompt   (validates, invokes the worker async, answers "accepted")
                     lambda_ws_worker   (invokes lambda_create, posts "result" to @connections)
client <------------ {"type": "result", ...}
```

#### How to use it, step by step

**1. Get a token.** Connections are authenticated with the Cognito user pool
Terraform creates (`cognito_user_pool_id` / `cognito_app_client_id` outputs).
Users are created by an administrator (self sign-up is off by default):

```bash
POOL=$(terraform -chdir=infra output -raw cognito_user_pool_id)
CLIENT=$(terraform -chdir=infra output -raw cognito_app_client_id)

# once per user
aws cognito-idp admin-create-user --user-pool-id "$POOL" --username alice@example.com --message-action SUPPRESS
aws cognito-idp admin-set-user-password --user-pool-id "$POOL" --username alice@example.com --password 'Str0ng!Passw0rd' --permanent

# every session: the access token is valid for 60 minutes
TOKEN=$(aws cognito-idp initiate-auth --client-id "$CLIENT" --auth-flow USER_PASSWORD_AUTH \
  --auth-parameters USERNAME=alice@example.com,PASSWORD='Str0ng!Passw0rd' \
  --query AuthenticationResult.AccessToken --output text)
```

Web apps get the same tokens through Amplify / `amazon-cognito-identity-js`
(SRP flow) with that pool and client id. Both the **access token** and the
**ID token** are accepted.

**2. Connect.** The URL is the `ws_api_url` Terraform output,
`wss://<id>.execute-api.<region>.amazonaws.com/<env>`. Send the token as
`Authorization: Bearer <token>` or, from a browser (which cannot set handshake
headers), as `?token=<token>` in the URL:

```bash
wscat -c "$(terraform -chdir=infra output -raw ws_api_url)" -H "Authorization: Bearer $TOKEN"
# or: wscat -c "$(terraform -chdir=infra output -raw ws_api_url)?token=$TOKEN"
```

A rejected handshake (missing, expired, forged token or a token of another pool
or app client) surfaces as an HTTP `401` on the upgrade: the socket never opens.
A `500` means the server side is misconfigured. The token is checked only on
`$connect`; the messages that follow on that connection need no token.

**3. Send the prompt.** Every message you send is a JSON object whose
`action` field picks the route. The only route is `prompt`:

```json
{ "action": "prompt", "prompt": "Generate a TO DO list application without Cognito authentication", "request_id": "my-id-1" }
```

| Field        | Required | Rules                                                                                                       |
| ------------ | -------- | ----------------------------------------------------------------------------------------------------------- |
| `action`     | yes      | Must be `"prompt"`; any other value is not routed to a Lambda and API Gateway answers nothing                |
| `prompt`     | yes      | Product description, non-empty after trimming                                                               |
| `request_id` | no       | Up to 64 characters; echoed in every answer so you can match them. A uuid4 hex is generated when absent     |

**4. Read the acknowledgement.** Within milliseconds you receive exactly one of:

```json
{ "type": "accepted", "request_id": "my-id-1" }
```

```json
{ "type": "error", "detail": "Invalid JSON body: Expecting value: line 1 column 1 (char 0)" }
{ "type": "error", "detail": [{ "type": "missing", "loc": ["prompt"], "msg": "Field required", "input": {"action": "prompt"} }] }
{ "type": "error", "detail": "Could not start the processing: ...", "request_id": "my-id-1" }
```

The three `error` shapes are, in order: the body is not JSON (`detail` is a
string), the body does not match the schema (`detail` is the list of Pydantic
errors; `request_id` is absent in both because nothing was parsed), and the
worker could not be started. After an `error` nothing else will arrive for
that request; fix the message and send it again.

**5. Wait for the result.** Tens of seconds later (up to ~5 minutes, the
timeout of `lambda_create`) you receive exactly one of:

```json
{ "type": "result", "request_id": "my-id-1", "result": { "analysis_date": "2026-10-26", "mermaid_diagram": "...", "aws_services": [...], "generated_code": {...}, "rag_references": [...] } }
```

```json
{ "type": "error", "request_id": "my-id-1", "detail": "Could not process the architecture: ..." }
```

`result` is exactly the body `lambda_create` returns over HTTP (`AWSArchitecture`
+ `rag_references`, see "Architecture generation"). The request is finished
either way; you may keep the connection open and send another prompt, or close.

**6. Reassemble large results.** API Gateway caps a WebSocket message at
128 KB and a complete architecture can exceed it. When the `result` message is
bigger than `WS_MAX_MESSAGE_BYTES` (120 KB), step 5 delivers the JSON text of
`result` in pieces instead, in order:

```json
{ "type": "result_chunk", "request_id": "my-id-1", "index": 0, "total": 3, "data": "{\"analysis_date\":\"2026-10-26\",\"mermaid_diag" }
{ "type": "result_chunk", "request_id": "my-id-1", "index": 1, "total": 3, "data": "ram\":\"graph LR..." }
{ "type": "result_chunk", "request_id": "my-id-1", "index": 2, "total": 3, "data": "...\"rag_references\":[]}" }
```

Concatenate `data` for `index` `0..total-1` and `JSON.parse` the string: the
outcome is the same object a `result` message carries. `data` is plain ASCII
(non-ASCII is `\uXXXX`-escaped), so pieces can be joined as text. A client
must therefore handle both `result` and `result_chunk`; a request ends when a
`result`, the last chunk or an `error` with its `request_id` arrives.

Messages of different requests can interleave on one connection (each worker
runs independently), so always dispatch on `request_id`. API Gateway closes
idle connections after 10 minutes and every connection after 2 hours; a result
pushed to a closed connection is logged by the worker and dropped, not
re-delivered, so keep the socket open until the answer arrives.

#### Example session

With [`wscat`](https://github.com/websockets/wscat) (`npm i -g wscat`):

```bash
wscat -c "$(terraform -chdir=infra output -raw ws_api_url)" -H "Authorization: Bearer $TOKEN"
> {"action": "prompt", "prompt": "Generate a TO DO list application without Cognito authentication", "request_id": "demo"}
< {"type": "accepted", "request_id": "demo"}
< {"type": "result", "request_id": "demo", "result": {"analysis_date": "2026-10-26", ...}}
```

The same session from a browser, handling every message type including chunk
reassembly:

```javascript
const ws = new WebSocket(`${wsApiUrl}?token=${accessToken}`);   // token from Amplify / Cognito
const chunks = {};                             // request_id -> data pieces

ws.onopen = () => ws.send(JSON.stringify({ action: "prompt", prompt: "Generate a TO DO list application", request_id: "demo" }));

ws.onmessage = ({ data }) => {
  const msg = JSON.parse(data);
  switch (msg.type) {
    case "accepted":     console.log("started", msg.request_id); break;
    case "error":        console.error(msg.request_id, msg.detail); break;
    case "result":       onArchitecture(msg.request_id, msg.result); break;
    case "result_chunk": {
      const parts = (chunks[msg.request_id] ??= []);
      parts[msg.index] = msg.data;
      if (parts.filter(Boolean).length === msg.total) {
        onArchitecture(msg.request_id, JSON.parse(parts.join("")));
        delete chunks[msg.request_id];
      }
    }
  }
};
```

The rest of this section describes the three Lambdas behind the routes; it is
only needed to change them, not to use the API.

#### `lambda_ws_connect` (`$connect`)

Decides whether the handshake is accepted. API Gateway only looks at the
status code (2xx accepts, anything else rejects; the body never reaches the
client). The token comes from `Authorization: Bearer <token>` or, since
browsers cannot set headers on a WebSocket handshake, from `?token=<token>` in
the connection URL. WebSocket APIs have no built-in Cognito/JWT authorizer
(HTTP and REST APIs only), so this function is the authorizer. The validation
is a strategy (`token_validator.TokenValidator`) chosen by `WS_AUTH_MODE`:

| `WS_AUTH_MODE`  | Behaviour                                                                                   |
| --------------- | ------------------------------------------------------------------------------------------- |
| `cognito`       | Accept a valid JWT of the Cognito user pool (deployed default, see below)                   |
| `shared_secret` | Accept only when the token equals `WS_AUTH_TOKEN` (fails closed)                            |
| `none`          | Accept every connection (default when the variable is unset; `-var ws_auth_mode=none` in Terraform) |

`CognitoValidator` (PyJWT) verifies the token's **signature** against the pool's
public keys (`<issuer>/.well-known/jwks.json`, downloaded once per container and
cached), its **issuer** (`https://cognito-idp.<region>.amazonaws.com/<pool id>`),
its **expiry**, that it is an **access token** (`token_use=access`, claim
`client_id`) or an **ID token** (`token_use=id`, claim `aud`) and that it was
issued for **our app client**. Anything else is a `401` with a reason in the
access logs (`invalid token: Signature has expired`, `... issued for another
app client`, ...). The token itself is never logged. A missing pool/client
configuration fails closed with `500`.

```
main.py -> orchestrator.py -> request_parser.py (input: models.ConnectionRequest)
                           -> service_auth.py -> token_validator.py (CognitoValidator | SharedSecretValidator | AllowAllValidator)
                           -> response.py (output: 200 accept / 401 reject / 500 misconfigured)
```

| Module               | Responsibility                                                              |
| -------------------- | --------------------------------------------------------------------------- |
| `main.py`            | Lambda handler; delegates to the orchestrator                               |
| `orchestrator.py`    | Runs parse -> authenticate -> response and maps failures to statuses        |
| `request_parser.py`  | Serializer: `$connect` event -> `models.ConnectionRequest` (token, id, IP) |
| `models.py`          | `ConnectionRequest` (input) and `AuthDecision` (allow / deny + reason)      |
| `token_validator.py` | `TokenValidator` protocol and its implementations (Cognito JWT, shared secret, allow all) |
| `service_auth.py`    | Registry `VALIDATORS` wired to `config`; builds the validator once per container |
| `response.py`        | Output: proxy response (only the status code matters to API Gateway)        |
| `config.py`          | `WS_AUTH_MODE`, `COGNITO_USER_POOL_ID`, `COGNITO_APP_CLIENT_ID`, `WS_AUTH_TOKEN` |

#### `lambda_ws_prompt` (`prompt`)

Validates the message and hands the job to the worker with an asynchronous
(`Event`) Lambda invocation, so it answers in milliseconds. The route has a
`$default` route response, which is what delivers its response body
(`accepted` / `error`) to the client. The job sent to the worker is
`{"connection_id", "callback_url", "request_id", "prompt"}`, where
`callback_url` is `https://<domainName>/<stage>` of the API (the `@connections`
endpoint), taken from the event's `requestContext`.

```
main.py -> orchestrator.py -> request_parser.py (input: models.ConnectionContext + models.PromptRequest)
                           -> models.WorkerJob -> service_dispatch.py (LambdaJobDispatcher: invoke Event)
                           -> response.py (output: accepted / error)
```

| Module                | Responsibility                                                                 |
| --------------------- | ------------------------------------------------------------------------------ |
| `main.py`             | Lambda handler; delegates to the orchestrator                                  |
| `orchestrator.py`     | Runs parse -> dispatch -> response and maps failures to statuses (400/422/500) |
| `request_parser.py`   | Serializer: event -> `ConnectionContext` (requestContext) and `PromptRequest` (body) |
| `models.py`           | `ConnectionContext`, `PromptRequest` (input) and `WorkerJob` (contract with the worker) |
| `service_dispatch.py` | `LambdaJobDispatcher`: asynchronous invocation of `WORKER_FUNCTION_NAME`       |
| `response.py`         | Output: proxy response with the `accepted` / `error` message                   |
| `config.py`           | `WORKER_FUNCTION_NAME`                                                         |

#### `lambda_ws_worker`

Invoked asynchronously with the job. It runs `lambda_create` with a synchronous
invocation (so the generation logic lives in exactly one place), unwraps its
proxy response and pushes the result to the client through the API Gateway
management API (`post_to_connection`). Failures are reported to the client as
an `error` message instead of raising, and Terraform sets the function's
asynchronous retries to 0, so a failed generation is never silently re-run. A
client that already disconnected (`GoneException`) is logged and ignored. The
`lambda` client waits `CREATE_TIMEOUT_SECONDS` (300 s, boto3's default of 60 s
would abort and retry the generation) with SDK retries disabled.

```
main.py -> orchestrator.py -> request_parser.py (input: models.Job)
                           -> service_generation.py (LambdaCreateGenerator: invoke lambda_create)
                           -> messages.py (result | result_chunk | error) -> service_publisher.py (ConnectionPublisher)
                           -> response.py (summary: completed / failed / rejected)
```

| Module                  | Responsibility                                                                   |
| ----------------------- | -------------------------------------------------------------------------------- |
| `main.py`               | Lambda handler; delegates to the orchestrator                                    |
| `orchestrator.py`       | Runs parse -> generate -> publish; reports generation failures to the client    |
| `request_parser.py`     | Serializer: invocation event -> `models.Job`                                     |
| `models.py`             | `Job` (the payload `lambda_ws_prompt` sends)                                     |
| `service_generation.py` | `LambdaCreateGenerator`: synchronous invocation of `CREATE_FUNCTION_NAME`        |
| `messages.py`           | Message formats and the splitting of large results into `result_chunk` messages |
| `service_publisher.py`  | `ConnectionPublisher`: `post_to_connection`, one client per callback URL         |
| `response.py`           | Summary returned by the handler (nobody waits for it; used by tests and logs)    |
| `config.py`             | `CREATE_FUNCTION_NAME`, `CREATE_TIMEOUT_SECONDS`, `WS_MAX_MESSAGE_BYTES`         |

Environment variables of the WebSocket Lambdas (set by Terraform in AWS):

| Variable                 | Lambda       | Required | Description                                                              |
| ------------------------ | ------------ | -------- | ------------------------------------------------------------------------ |
| `WS_AUTH_MODE`           | `ws_connect` | no       | `cognito` (deployed default), `shared_secret` or `none` (default when unset) |
| `COGNITO_USER_POOL_ID`   | `ws_connect` | yes*     | User pool whose tokens are accepted (*when `WS_AUTH_MODE=cognito`)       |
| `COGNITO_APP_CLIENT_ID`  | `ws_connect` | yes*     | App client the tokens must be issued for (*when `WS_AUTH_MODE=cognito`)  |
| `WS_AUTH_TOKEN`          | `ws_connect` | no*      | Secret clients must present (*required when `WS_AUTH_MODE=shared_secret`) |
| `WORKER_FUNCTION_NAME`   | `ws_prompt`  | yes      | Name of `lambda_ws_worker`                                               |
| `CREATE_FUNCTION_NAME`   | `ws_worker`  | yes      | Name of `lambda_create`                                                  |
| `CREATE_TIMEOUT_SECONDS` | `ws_worker`  | no       | How long to wait for `lambda_create` (default 300)                       |
| `WS_MAX_MESSAGE_BYTES`   | `ws_worker`  | no       | Largest message pushed to a client (default 122880, API limit is 128 KB) |

## Prerequisites

- Python 3.12 (the Lambda runtime)
- A virtual environment, e.g. `project-starter/.venv`
- Dependencies installed from [requirements-dev.txt](requirements-dev.txt)
  (`requirements.txt` holds only what goes into the Lambda layer; `boto3` is
  provided by the Lambda runtime and is therefore listed as a dev dependency)

### Environment variables

| Variable         | Required | Description                                                                                                                                       |
| ---------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GROQ_API_KEY`   | yes      | Key of the Groq model used to generate the architectures                                                                                          |
| `RAG_S3_BUCKET`  | yes*     | Bucket that stores `rag_index.json` (*not needed when `RAG_INDEX_PATH` exists)                                                                    |
| `RAG_S3_KEY`     | no       | Object key of the index inside the bucket (default `rag_index.json`)                                                                              |
| `RAG_INDEX_PATH` | no       | Local path of the index (default `/tmp/rag_index.json`). If the file exists, the S3 download is skipped                                           |
| `CORS_ORIGINS`   | no       | Comma-separated browser origins echoed in `Access-Control-Allow-Origin`. Leave it unset when CORS is configured on the Function URL              |

In AWS these are set by Terraform (`infra/main.tf`). Locally, put them in
`backend-ia/.env` (git-ignored): `config.py` loads that file on import, without
overriding variables already present in the shell. Start from
[`backend-ia/.env.example`](../.env.example).

## How the RAG works

The index is generated locally by `backend-ia/rag/ingest.py`: it reads the
reference Python files, splits them into chunks (1000 characters, 200 of
overlap, Python-aware splitter) and writes them to `rag_index.json`. No
embeddings are generated: the Lambda searches the chunks with BM25 (keyword
ranking, pure Python), which is what keeps the package small enough for a zip.

1. Build the index (always pass `--source`; without it the script indexes this
   API's own code, which is useless as a reference):

   ```bash
   cd backend-ia
   python rag/ingest.py --source <folder with the reference .py files> --output rag_index.json
   ```

2. Upload it to the bucket of the environment (dev = `sandbox-<RAG_BUCKET>`):

   ```bash
   aws s3 cp rag_index.json s3://sandbox-project-starter-backend-ia-rag/rag_index.json
   ```

On the first invocation of a container the Lambda downloads the file to
`RAG_INDEX_PATH` and builds the BM25 index in memory; warm invocations reuse
both, as well as the Groq client. After uploading a new index, running containers
keep the old copy until they are recycled; redeploy (or wait) to refresh them.
Terraform grants the function `s3:GetObject` on that single object only, so a
missing file shows up as a `403 Forbidden` (S3 hides 404 without `ListBucket`).

The query is enriched with AWS/serverless terms before the search and the three
best chunks are sent to Groq as `[CONTEXTO RAG]`.

## Request and response

Send a JSON body:

```json
{
  "prompt": "Generate a TO DO list application without Cognito authentication"
}
```

```bash
curl -X POST "$(terraform -chdir=infra output -raw lambda_create_url)" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Generate a TO DO list application without Cognito authentication"}'
```

Over the WebSocket API the same request is `{"action": "prompt", "prompt": "..."}`
(see "WebSocket API").

The handler always returns an API Gateway proxy response
(`statusCode`, `headers`, `body`); REST API (v1) and HTTP API / Function URL
(v2) events are both accepted. Status codes:

| Status | Meaning                                                              |
| ------ | -------------------------------------------------------------------- |
| 200    | Architecture generated (`rag_references` lists the RAG sources used) |
| 400    | Body is not valid JSON                                               |
| 422    | Body does not match the schema (`prompt` is required)                |
| 500    | Generation failed                                                    |

Errors carry a `{"detail": ...}` body.

## Run locally

Each Lambda folder has its own `run_local.py`, which calls `main.lambda_handler`
exactly as the Lambda runtime does: it loads `backend-ia/.env`, builds the
proxy event and prints the response. Nothing is mocked: Groq, S3 and your AWS
credentials are really used. The scripts are deliberately tiny (one per Lambda,
so two people working on different Lambdas never touch the same file) and are
driven by variables at the top instead of command-line options:

| Variable         | In               | Purpose                                                          |
| ---------------- | ---------------- | ---------------------------------------------------------------- |
| `EVENT`          | both             | The event passed to `main.lambda_handler` (API Gateway payload 2.0) |
| `PROMPT`         | `lambda_create`  | Product description placed in `EVENT["body"]`                    |
| `WRITE_CODE_DIR` | `lambda_create`  | Folder to dump the generated Terraform/Python files (`None` = off) |

1. **Install the dev dependencies** (once):

   ```bash
   cd backend-ia/api
   python -m venv ../../.venv && source ../../.venv/bin/activate   # Windows: ..\..\.venv\Scripts\activate
   python -m pip install -r requirements-dev.txt
   ```

2. **Create `backend-ia/.env`** from the example and set `GROQ_API_KEY`:

   ```bash
   cp ../.env.example ../.env
   ```

3. **Get a RAG index** (only for `lambda_create`). Either build one locally (no AWS needed):

   ```bash
   python ../rag/ingest.py --source <folder with the reference .py files> --output ../rag_index.json
   ```

   `lambda_create/run_local.py` uses `RAG_INDEX_PATH` from `.env` (relative to
   `backend-ia/`) or, failing that, `backend-ia/rag_index.json`. When neither
   exists it falls back to `RAG_S3_BUCKET`, like the deployed function.

4. **Invoke** (edit the variables first if needed):

   ```bash
   python lambda_status/run_local.py       # health check: are .env and AWS credentials good?
   python lambda_create/run_local.py       # generates an architecture
   python lambda_ws_connect/run_local.py   # $connect: is TOKEN accepted? (COGNITO_* in .env, no AWS credentials)
   python lambda_ws_prompt/run_local.py    # prompt: invokes the deployed worker (WORKER_FUNCTION_NAME)
   python lambda_ws_worker/run_local.py    # worker: runs the deployed lambda_create (CREATE_FUNCTION_NAME)
   ```

   The WebSocket scripts talk to deployed functions, so they need AWS
   credentials and the function names in `.env` (see `.env-example`);
   `ws_prompt`/`ws_worker` push the answer to `CONNECTION_ID`, so either paste
   the id of a client connected right now (it appears in the API's access logs)
   or expect a "connection is gone" warning.

   The exit code is `0` on HTTP 200 and `1` otherwise (including the `503` of an
   unhealthy check), so they can be used in scripts. To simulate a request
   copied from the AWS console, paste it into `EVENT`.

What each script does, in order: load `.env` -> (`create` only) point
`RAG_INDEX_PATH` at a local index -> import `main` (only now, because
`config.py` reads the environment at import time) -> call the handler with
`EVENT` -> print the status and body -> (`create` only, when `WRITE_CODE_DIR`
is set) write the generated files. Terraform excludes `run_local.py` from the
zips, so it never reaches AWS.

### Tests

```bash
cd backend-ia/api
python -m pytest                       # everything
python -m pytest tests/lambda_status   # one Lambda only
```

The tests never call Groq, S3, Lambda or API Gateway (everything external is
mocked) and run in CI on every pull request. There is one folder per Lambda,
each with its own `conftest.py` (fixtures and `sys.path` setup for that
Lambda's flat modules):

```
tests/
  lambda_modules.py    isolated_lambda(): loads one Lambda's flat modules without clashing with the others'
  lambda_create/       test_main.py, test_orchestrator.py, test_machine.py, ...
  lambda_status/       test_main.py (handler), test_checks.py (each health check)
  lambda_ws_connect/   test_token_validator.py, test_service_auth.py, test_orchestrator.py, ...
  lambda_ws_prompt/    test_service_dispatch.py, test_request_parser.py, test_orchestrator.py, ...
  lambda_ws_worker/    test_messages.py (chunking), test_service_generation.py, test_service_publisher.py, ...
```

Because every zip is flat, all Lambdas have modules with the same names
(`main`, `orchestrator`, `config`, ...). `tests/lambda_modules.py` imports one
Lambda's modules with its folder first on `sys.path` and swaps them into
`sys.modules` only for the duration of each test; the `conftest.py` of each
WebSocket folder exposes them as a fixture (`ws_connect`, `ws_prompt`,
`ws_worker`), e.g. `ws_worker.orchestrator.handle(event)`.

## Deploying

Deployment is done by Terraform (`infra/`) through the **Deploy Lambdas** GitHub
workflow (`.github/workflows/deploy.yml`): it runs the tests, zips each Lambda
folder (flat, `main.py` at the root), builds one dependencies layer per folder
from its `requirements.txt`, creates a public Function URL for `lambda_create`
and `lambda_status`, wires the WebSocket Lambdas behind API Gateway (routes
`$connect` and `prompt`) and applies to the environment's AWS account. It runs
automatically on pushes to `main` (development) and manually for stage/prod.

Authentication is `infra/modules/cognito`: a user pool (e-mail sign-in, strong
passwords, admin-created users unless `-var cognito_allow_self_signup=true`,
deletion protection in prod) and one public app client (no secret; SRP for
browsers, `USER_PASSWORD_AUTH` for the CLI; tokens valid 60 minutes, refresh
30 days). Its ids are passed to `lambda_ws_connect`, which verifies the tokens
(`ws_auth_mode`, default `cognito`). Terraform does not create users.

The WebSocket API is `infra/modules/apigateway_websocket`, the only API Gateway
of the stack: one Lambda proxy integration per route, a `$default`
route response for the routes that answer the client, an explicit deployment
(WebSocket stages have no auto-deploy) and a named stage (`var.environment`),
so the URL is `wss://<id>.execute-api.<region>.amazonaws.com/<env>`
(`terraform output ws_api_url`). The three WebSocket Lambdas have no public
Function URL; `lambda_ws_prompt` may only invoke the worker and
`lambda_ws_worker` may only invoke `lambda_create` and call
`execute-api:ManageConnections` on this API.

A WebSocket stage can only write access logs when API
Gateway's **account-level** "CloudWatch Logs role ARN" is set (otherwise
`CreateStage` fails with `CloudWatch Logs role ARN must be set in account
settings to enable logging`). `infra/apigateway_account.tf` creates that role
(`AmazonAPIGatewayPushToCloudWatchLogs`) and sets it with
`aws_api_gateway_account`; the WebSocket module waits for it. It is one setting
per AWS account and region, so if another stack already owns it use
`-var manage_api_gateway_account=false`, and to deploy without access logs at
all use `-var ws_access_logs=false`.

Terraform does **not** create the RAG bucket nor upload the index: do that once
per environment (see "How the RAG works").

### Permissions of the deploy user

The IAM user behind `AWS_ACCESS_KEY_ID` (`github-deploy`) is created by hand,
outside Terraform, and its policy must cover every service the stack touches.
The WebSocket API (`infra/modules/apigateway_websocket`) requires the extra permissions in
[`infra/policies/github-deploy-api-gateway.json`](../../infra/policies/github-deploy-api-gateway.json):
API Gateway v2 APIs **and their tags** (the provider's `default_tags` make
`CreateApi` call the `/tags` endpoint), `lambda:AddPermission` for the routes,
and the `/aws/apigateway/*` access log group. The worker additionally needs the
deploy user to manage its asynchronous-invocation config
(`lambda:PutFunctionEventInvokeConfig`, `lambda:GetFunctionEventInvokeConfig`,
`lambda:UpdateFunctionEventInvokeConfig`, `lambda:DeleteFunctionEventInvokeConfig`)
and the account-level logging role: `apigateway:GET`/`apigateway:PATCH` on
`arn:aws:apigateway:<region>::/account` plus `iam:PassRole` on
`<env>-backend-ia-apigateway-logs-role` (role creation itself is already
covered by the permissions the Lambda execution roles need). The Cognito module
needs `cognito-idp:CreateUserPool`, `cognito-idp:CreateUserPoolClient` and the
matching `Describe*`, `Update*`, `Delete*`, `TagResource`/`UntagResource`/
`ListTagsForResource` actions on `arn:aws:cognito-idp:<region>:<account>:userpool/*`.
Attach it once per AWS account:

```bash
aws iam put-user-policy \
  --user-name github-deploy \
  --policy-name backend-ia-api-gateway \
  --policy-document file://infra/policies/github-deploy-api-gateway.json
```

Without it the apply fails with `AccessDeniedException: ... is not authorized to
perform: apigateway:POST on resource: arn:aws:apigateway:us-east-2::/tags/...`. For browser
calls to the Function URL, configure CORS on the Function URL (the function
only echoes `CORS_ORIGINS`; it does not answer `OPTIONS` preflights).

Because the endpoint is public, consider a concurrency limit
(`reserved_concurrent_executions`) or API Gateway throttling to avoid abuse of
the Groq quota.

Do not put real keys in commands, documentation, or commits. If a key has been
exposed, revoke it and generate a new one with the corresponding provider.
