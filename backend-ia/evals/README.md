# Evals

Automated tests for measuring the quality of architectures generated by `POST /create`.

The idea is simple: a fixed list of requests (`prompts.json`) is sent to the API, each response passes through automated validators, and the result becomes a **score comparable across runs**. A system change (prompt, RAG, model, Terraform template) is accepted only if the score increases or stays the same.

## Estrutura

```
evals/
├── baseline/resultado_arquitetura.json   # known bad output (should fail)
├── results/                              # one run per file (YYYY-MM-DD_HHMM.json)
├── prompts.json                          # test cases and expectations for each one
├── validators.py                         # functions that report errors
├── run_evals.py                          # runs all cases against the API
├── check_baseline.py                     # tests validators without calling the API
├── NOTAS.md                              # score history by change
└── README.md
```

## Requirements

- Python 3.10+
- `pip install requests python-dotenv`
- Terraform installed and available on PATH (`terraform version` must work in the same terminal). Without it, the `terraform` validator fails every case.
- API running (`cd api && uvicorn main:app --host 0.0.0.0 --port 8000`)
- `GROQ_API_KEY` set in `.env`, because the API uses the model hosted by Groq
- `API_SECRET` set in `.env` to authenticate requests

Recommended for speeding up `terraform init` (downloads the AWS provider):

```bash
mkdir -p ~/.terraform-cache
export TF_PLUGIN_CACHE_DIR=~/.terraform-cache
```

## Running

Run the commands below from `backend-ia/`, with the API in another terminal:

```bash
# 1. Check all JSON files in evals/baseline (does not use the API)
python evals/check_baseline.py

# 2. Run all cases against the API
python evals/run_evals.py
```

## Manual prompt workflow

To test the CRUD prompt used in `scripts/call_api.py`:

```bash
python scripts/call_api.py
```

With HTTP `200`, the generated file is saved to
`backend-ia/resultado_arquitetura.json`. For `check_baseline.py` to read it,
move it to the expected directory:

```bash
mv resultado_arquitetura.json evals/baseline/resultado_arquitetura.json
python evals/check_baseline.py
```

Use `cp` instead of `mv` to preserve the file at the root. The check command
processes every `*.json` file in `evals/baseline`, so remove or rename old
results if you want to evaluate only one file.

The current manual prompt is:

```text
To-do list application. The user can create a task, list all tasks, retrieve a task by ID, update a task, and remove a task.
```

```
  consistencia: X/12
  terraform: X/12

Details saved to evals/results/2026-09-29_1030.json
```

A case only **passes** if all validators approve it. API errors (timeout, 401, 500, invalid model JSON) count as failures and the runner continues.

## Validators

Each validator receives `(result, expected)` and returns a list of errors. An empty list means the case passed.

| Name | What it checks |
|---|---|
| `python` | Valid syntax (`ast.parse`), no `httpMethod`, no direct `return json.dumps(`, no reading `region`/`table_name` from the `event` |
| `tf_nao_vazio` | Terraform has at least 3 resources. Prevents the other validators from approving an empty result |
| `regras_tf` | No `source_arn = "*"` and Python runtime >= 3.10 |
| `consistencia` | Number of `.py` files equals the number of `aws_lambda_function` resources; equals the expected count; roles and permissions for each Lambda; required resources are present |
| `terraform` | `terraform init -backend=false` and `terraform validate` in a temporary directory |

To add a validator, write the function in `validators.py` and register it in the `VALIDATORS` dictionary. The runner uses the dictionary, so nothing else needs to change.

## Test cases (`prompts.json`)

```json
{
  "id": "crud-basic",
  "prompt": "CRUD API for items with DynamoDB",
  "esperado": {
    "lambdas": 4,
    "recursos": ["aws_dynamodb_table", "aws_api_gateway_rest_api"]
  }
}
```

- `id`: short case name.
- `prompt`: request sent to the API.
- `esperado.lambdas`: number of Lambdas that should exist.
- `esperado.recursos`: Terraform resource types that should appear.

The `esperado` field may contain only what a machine can verify. "Good code" is not a test.

The 12 cases cover: CRUD (with wording variations), read-only, create-only, delete-only, two entities, SQS queue, S3 upload, Cognito authentication, and a scheduled Lambda. Difficult cases tend to fail at first, and that is expected.

Watch for false positives: if the model uses `aws_apigatewayv2_api` instead of `aws_api_gateway_rest_api`, the validator fails a result that may be correct. In that case, adjust `esperado`, not the system.

## Workflow

1. **Validator baseline:** place the JSON in `evals/baseline/` and run `python evals/check_baseline.py`. The script uses `esperado = {"lambdas": 5, ...}` defined in `check_baseline.py`, which differs from the cases in `prompts.json`. If a validator approves something that should fail, fix the validator before continuing.
2. **Initial score:** run `run_evals.py` 2 or 3 times and record the average. This shows the model's natural variation.
3. **Record it in `NOTAS.md`:** one line per change, describing what was changed.
4. **Change one thing at a time** and run again. If the score increases, keep it. If it drops or stays the same, revert or investigate.
5. **Diagnose failures:** open the `saida` field for a case in `results/` and inspect what the model generated.

### Reducing noise

During evals, use `temperature=0.1` and `do_sample=True` in `machine.py`. With a high temperature, the score fluctuates even without code changes.

## Reading results

| What you see | Meaning | Next step |
|---|---|---|
| Many `erro_api` errors (parser, timeout) | Large JSON is fragile | Staged generation: JSON plan, one file per call |
| Low `python` score | Model produces invalid syntax | Repair loop with `ast.parse` returning the error to the model |
| Low `consistencia` and `terraform` scores | Model produces invalid Terraform | Template-based Terraform (Jinja) |
| Only difficult cases fail | The basics work | Adjust the RAG (index `.tf`, exclude tests) |
| Same score with old and new prompts | The prompt is not the bottleneck | Do not spend more time on it |

### Results observed with the manual prompt

The `scripts/call_api.py` runs returned HTTP `200` and saved the JSON. However, the
validators found different problems in each generation:

- initial generation: missing imports (`os` and `logging`), one Lambda for four
  Python files, and only one route;
- next generation: five Lambdas, but invalid Terraform due to a duplicate
  `output "api_url"`;
- next generation: `stage_name` used directly in
  `aws_api_gateway_deployment`, an unsupported argument;
- most recent generation: consistency and routes passed, but `terraform validate`
  failed because `lambda/create_task.zip` and other artifacts referenced by
  `filebase64sha256` do not exist.

This means the request and validators are running; the failures are in the
Terraform and generated code. Before interpreting the score, fix the reported
error and run the check again. The Terraform validator requires Terraform to be
installed and the `.zip` files expected by the result.

Beware of misleading results: a 12/12 column may be a false positive (for example, `regras_tf` approves when there are no Lambdas in the Terraform). That is why `tf_nao_vazio` exists. A 0/12 column may also be an environment issue (Terraform not installed), not a model issue.

## Quick result diagnosis

Run from `backend/`:

```python
import json
from pathlib import Path

files = sorted(Path("evals/results").glob("*.json"))
results = json.loads(files[-1].read_text(encoding="utf-8"))

for result in results:
    output = result.get("saida")
    if not output:
        print(result["id"], "| no output:", result["erro_api"])
        continue
    terraform = output["generated_code"]["terraform"]
    python_files = output["generated_code"]["python"]
    all_terraform = "\n".join(terraform.values())
    print(
        result["id"],
        "| terraform files:",
        list(terraform),
        "| resources:",
        all_terraform.count('resource "'),
        "| python:",
        [name for name in python_files if name.endswith(".py")],
    )
```

## Known limitations

- The validators check structure and static rules. They do not execute Lambdas or run `terraform plan/apply`.
- `terraform validate` does not detect excessive permissions or bad practices. Consider adding `tflint` and `checkov` for that.
- Resource regex checks do not understand modules or `count`/`for_each`.
- The model is stochastic: consider an improvement only if it exceeds the variation measured across identical runs.
